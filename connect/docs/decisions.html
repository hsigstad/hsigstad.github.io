    2026-03-19 — Sample: TRT labor courts, 2014–2018

    Decision: Estimate effects on cases filed in Brazilian labor courts (Justiça do Trabalho / TRT) over 2014–2018.

    Reason: TRT uses deterministic random assignment of cases to judges within the vara (court unit), which is the design leveraged for identification. 2014 is the first year of reliable electronic filing records across most TRTs; 2018 is the last year with settled case outcomes available.

    Alternatives considered: TJ (state civil courts) — rejected as the primary sample because assignment rules vary across states and are less uniformly random. TJ joint-case data still used as an auxiliary connection source.

    2026-03-19 — Identification: random assignment of cases within vara × filing-year

    Decision: Identify the effect of lawyer–judge connections by comparing cases filed in the same vara × filing-year where the lawyer is connected to at least one of the assignment pool's judges, exploiting random case-to-judge assignment within the pool.

    Reason: Within a vara × filing-year, which judge a case lands on is random conditional on the pool of active judges. A plaintiff's lawyer who is connected to one judge in the pool gets treated if the case happens to draw that judge. The counterfactual is drawing one of the other pool judges.

    Alternatives considered: Judge fixed effects on levels (cannot separate judge leniency from connection effects); matching on observables (no credible source of exogenous variation).

    Implications: Specification uses vara × filing-year fixed effects (the randomization strata). Pre-filed lawyer choice is part of the design, not a threat, because the assignment happens after filing.

    2026-03-19 — Weighting: IPW by connection propensity

    Decision: Weight cases by the inverse probability that the assigned judge is one of the lawyer's connected judges, computed per vara × filing-year.

    Reason: Cases whose lawyer is connected to many judges in the pool have a mechanically higher probability of treatment than cases connected to one judge. Unweighted OLS would over-represent the many-connection cases and blur the marginal effect of a single connection. IPW restores the ATE of "one additional connected judge present in the draw."

    Alternatives considered: Judge-pool fixed effects alone (handles differential exposure by conditioning, but loses power on many-connection cases); stratified regression by number-of-connections (noisier and harder to interpret as a single parameter).

    Implications: Requires an accurate count of each case's connected judges in the pool. The IPW weights are constructed in source/query/TRT/proc_isautor__adv_connection.R.

    2026-03-19 — Connection types: relatives + colleagues of relatives

    Decision: Define treatment as a binary indicator for any connection, then run heterogeneity by type: (i) close relatives of judge (spouse, child, parent, sibling), (ii) extended family, (iii) colleagues of relatives (same law firm / socio / shared address).

    Reason: Close-relative connections are the cleanest conceptually but rare; colleague-of-relative connections are more frequent and plausibly capture the same patronage channel with less precision. Running them together pools power; running by type identifies which channel matters.

    Alternatives considered: Close relatives only (clean but statistically underpowered); a continuous "strength" score (less interpretable, and the underlying data do not support a credible ordering).

    Implications: Heterogeneity table in paper/tables/by_connection_tp.tex. Power concern tracked as an open todo.md item.

    2026-03-19 — Randomization test as the primary identification check

    Decision: Validate as-good-as-random assignment by running a regression of case characteristics (value, topic dummies, plaintiff vs defendant) on the connected-judge indicator with the same vara × filing-year fixed effects as the main specification.

    Reason: If assignment is random within stratum, case characteristics should not predict which cases draw a connected judge. A significant F-statistic would reveal non-random assignment or lawyer manipulation of filing timing/vara.

    Alternatives considered: Eyeballing balance tables (less formal; does not account for within-stratum clustering).

    Implications: Table produced by source/table/paper/adv_randomization.R. Known failure mode for courts with >20 varas is an open todo.md item.

    2026-03-27 — Column naming: standardise to full form, keep foro vs randunit distinct

    Decision: Rename all adv_* columns to advogado_* (e.g., adv_cpf → advogado_cpf). Do not collapse foro and randunit.

    Reason: Full-form names match the rest of the pipeline (processo_*, juiz_*). foro is the physical courthouse and randunit is the randomization stratum — they coincide for most TRTs but not all. Collapsing them would silently break identification in TRTs where assignment pools cross foros.

    Alternatives considered: Keep adv_* (saves typing but breaks convention); treat foro = randunit everywhere (cleaner but wrong in some TRTs).

    Implications: All server scripts and the synthetic data generator use the full-form names. pathmap.py does not rewrite these.

    2026-03-27 — Table script organisation: paper / descriptive / exploratory

    Decision: Split bocconi/source/table/ into paper/ (tables in the manuscript, built by SConstruct), descriptive/ (shown to collaborators but not in the paper), exploratory/ (one-off checks).

    Reason: The table directory had grown to 50+ scripts with no way to tell which were load-bearing. Only paper/ scripts need to survive refactors; the other two can rot.

    Alternatives considered: One flat directory with a naming convention (noisier); pruning everything not currently in the paper (loses context).

    Implications: SConstruct tracks only paper/ scripts. Column renames and schema changes are required to keep paper/ scripts green but not the others.

    2026-04-13 — Parse pipeline treated as a pre-existing external

    Decision: Do not rebuild pipelines/bocconi/justica/source/parse/ locally. Instead, SConstruct treats relator_{estadual,federal}.csv as stubs (empty shells) so downstream scripts run end-to-end on synthetic data.

    Reason: parse/parte.py imports a stale diarios API (from parse_diario import ..., import clean) that no longer exists in the current package. Reconstructing that API would require diarios archaeology and is not on the critical path for method development on synthetic data.

    Alternatives considered: Fix parse/ against the current diarios API (high effort, blocked on understanding the old API); remove desembargador detection (loses the appeals-court variable).

    Implications: All judges are assigned desembargador = FALSE in the synthetic build. Restoring parse/ is an open todo.md item; until then, results that depend on desembargador are invalid locally but still run on the server (where the old parse outputs exist).

    2026-04-13 — Metadata snapshots tracked under build/

    Decision: Track bocconi/build/extract/metadata/ in git (schemas, distributions, cross-tabs) via an explicit !bocconi/build/extract/metadata/ override in .gitignore.

    Reason: The metadata was generated on the Bocconi server and exported via the manual approval flow. Regenerating it requires server access, so the normal "build/ is regenerable" invariant does not hold. Committing the snapshots lets local development reference server schemas without re-exporting.

    Alternatives considered: Keep metadata outside the repo (requires a parallel store); regenerate locally from synthetic data (would lose the server distributions, which are the point).

    Implications: Any change to the metadata requires a fresh server export and an approval step. The negation pattern in .gitignore is a documented exception to the "build is regenerable" rule.
