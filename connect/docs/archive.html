      • 192 of 3000 judges have multiple spouses; typically 4 years between
      • Unlikely to work

    Plan: Synthetic Raw Data for Full Pipeline Testing

    Created: 2026-03-25

    Context

    We need synthetic data so we can develop/debug R/Stata/Python scripts locally with Claude Code, then transfer finalized scripts to the Bocconi secure server. The server has restricted exports (25MB .zip, output only, no primary data).

    Approach: Synthesize all raw data sources at small scale

    Generate a miniature but internally-consistent synthetic universe that mirrors the real raw data on the server. The full pipeline (justica, familia, economia -> connect) runs end-to-end on this synthetic data. This is a long-term investment: any new project using these same data sources gets synthetic data for free.

    "Synthetic Brazil" scale:

    • ~1,000 people (judges, lawyers, litigants, relatives) with synthetic CPFs
    • Multiple foros of varying sizes: 1 large (20+ varas, passes randomization filters), 3-4 medium (5-10 varas), a few small (2-3 varas) -- realistic variation
    • ~50 judges, ~400 lawyers, ~50 with family connections to judges
    • ~100,000 labor court cases (5 years x ~20k/year, distributed across foros)

    Original content:

    AI-Assisted Development Workflow

    The real data and existing codebase live on a Bocconi secure server without internet access. This note documents the options we evaluated for using AI coding tools and the chosen workflow.

    Chosen approach: Option 1

    Develop and debug code locally with Claude Code using synthetic data. Transfer finalized scripts to the Bocconi server. Iterate: inspect error logs (no data) on server, fix locally, re-transfer.

    All options considered (2026-03-19)

    Option 1: Synthetic data + local development (chosen)

    • Generate synthetic data mimicking the real data's structure and distributions
    • Full access to frontier AI tools (Claude Code with Opus/Sonnet) during development
    • Transfer clean scripts to server via approved channels
    • Pro: Best model quality. No data leaves server. Standard workflow among economists with restricted data.
    • Con: Synthetic data won't capture all edge cases. Data-specific debugging requires manual inspection on server.

    Option 2: AWS Bedrock + VPC PrivateLink

    • Claude available on Bedrock with private endpoints (traffic stays within AWS network)
    • Claude Code natively supports Bedrock as backend
    • Pro: Frontier model quality directly on server.
    • Con: Server needs network access to AWS VPC. Requires institutional IT buy-in. Not truly air-gapped.

    Option 3: Ollama + Aider on the server

    • Install Ollama with local model (e.g., Qwen3-Coder 32B) on the secure server
    • Run Aider (terminal-based, git-native AI pair programming) against it
    • Model weights transferred via approved media (USB, secure file transfer)
    • Fully air-gapped — zero network needed
    • Pro: AI assistance directly where the data lives.
    • Con: Local models noticeably weaker than Claude Sonnet/Opus for complex reasoning. Needs GPU (~24GB VRAM for 32B model).

    Option 4: Claude Code + local model via proxy

    • Claude Code supports ANTHROPIC_BASE_URL pointed at a local Ollama instance
    • Same quality limitations as option 3, but keeps the Claude Code UX
    • Pro: Familiar interface.
    • Con: Still limited by local model quality. Some Claude Code features may not work with non-Anthropic models.

    Notes

    • Anthropic does not distribute model weights — no on-premise Claude deployment exists
    • Claude Code cannot run fully offline (always needs an API backend)
    • If the Bocconi server gets a GPU, option 3 is worth revisiting for server-side debugging
    • If the server has any VPC connectivity, option 2 gives the best quality/convenience tradeoff

    Reason for archiving:

    • Decision made (Option 1, synthetic + local) and subsequently superseded by direct server pipeline run. Options catalogue preserved for future reference if workflow is revisited.

    #+TITLE: New specifications

    • Specification 1
    • A firm has an important case randomly assigned Judge A
    • Does this increase the probability of hiring a relative of Judge A in another case?

    *** Details

    • Sample: All cases with valor da causa above certain threshold
    • One observation per case x judge in randomization unit
    • Possible schemes:
      1. A's relative hired before final decision. Judge then reciprocates. Requires firm to trust judge.
      2. A's relative hired after final decision as a reward to judge. Requires judge to trust firm.
      3. A combination of 1 and 2

    Firm more likely to be trusted if

    • A repeat litigant

    Judge more likely to be trusted if

    • Few judges in the district
    • In the district for a long period

    The use of middlemen:

    • A "middleman" lawyer with repeated interactions both with firm and judge can create trust
    • How it could work:
      • The middleman promises the firm a favorable decision if the firm hires the judge's relative.
      • The firm trusts the middleman due to firm-middleman repeated interaction
      • The middleman trusts the judge to reciprocate due to judge-middelman repeated interaction
    • The middleman could be on an incentive contract (being payed conditional on winning the case). In that case, there is no need for trust/repeated interactions between the firm and the middleman.

    We can perhaps identify "middleman lawyers" tied to certain judges by them being involved in disproportionally many cases in the judge's vara compared to other varas in the same court.
